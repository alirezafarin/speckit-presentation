Constitution

DNA معماری پروژه در memory/constitution.md

constitution فایلی است که قوانین ثابت پروژه را نگه می‌دارد. agent قبل از هر plan آن را می‌خواند و plan باید بخش Constitutional Compliance را پاس کند. همه مثال‌های زیر روی همان فیچر onboarding اسلاید ۱۶ است.

منطق فیچر اول در یک پکیج مستقل نوشته می‌شود تا بدون UI هم قابل تست و استفاده باشد. درست: packages/onboarding → nextStep(), validateStep()
نادرست: apps/web/app/onboarding/page.tsx → nextStep()

همان پکیج باید از ترمینال هم اجرا شود تا رفتارش بدون مرورگر قابل بازرسی باشد: ورودی و خروجی متنی و JSON. onboarding-cli validate --json < profile.json

اول تست نوشته و تأیید می‌شود و باید شکست بخورد؛ بعد کد نوشته می‌شود. 1. onboarding.test.ts → expect(nextStep('PROFILE')).toBe('PREFERENCES') → FAIL
2. nextStep() → PASS

کامپوننتی که بیش از یک اپ لازم دارد به پکیج مشترک می‌رود؛ کامپوننت مختص یک اپ داخل همان اپ می‌ماند. درست: packages/ui/src/Stepper.tsx → apps/web + apps/admin
نادرست: apps/web/components/Stepper.tsx + apps/admin/components/Stepper.tsx

واکشی داده در Server Component انجام می‌شود و 'use client' فقط به کامپوننت برگِ تعاملی می‌رسد. درست: app/onboarding/page.tsx → await getOnboardingState()
درست: OnboardingForm.tsx → 'use client'
نادرست: app/onboarding/page.tsx → 'use client'

پوشه نصب

داخل .specify/ دقیقاً چه چیزی نصب شده است؟

.specify/ پوشهٔ نصب Spec Kit است، نه spec محصول. روی هر گره کلیک کنید تا نقش واقعی آن فایل را ببینید. این درخت از نصب واقعی همین پروژه گرفته شده است: نسخهٔ ۱.۰.۴، ایجنت cursor-agent، اسکریپت bash.

یک فایل را انتخاب کنید

این پوشه چهار دستهٔ کاملاً متفاوت دارد:

  • پیکربندی نصب در ریشه: چه چیزی و برای کدام ایجنت نصب شده
  • قانون پروژه در memory/
  • قالب‌های خالی در templates/
  • اسکریپت‌های اجرایی در scripts/bash/

دو مانیفست هم فقط رسید نصب هستند.

نکتهٔ مهم برای این تیم: چون invoke_separator در integration.json برابر - است، فرمان‌های ما /speckit-specify نوشته می‌شوند، در حالی که مستندات رسمی /speckit.specify را نشان می‌دهد. کارکرد یکی است.

اسکریپت‌ها

نیمهٔ قطعی Spec Kit: scripts/bash/

skill کرسر متن می‌نویسد، اسکریپت‌ها مسیر می‌سازند. ایجنت آن‌ها را با --json صدا می‌زند تا مسیر و قالب را بخواند، نه اینکه نام پوشه از خودش دربیاورد. 

     you / Cursor skill  /speckit-specify, /speckit-plan, …
runs →  .specify/scripts/bash/*.sh        create dirs, check files, resolve paths
copies →  .specify/templates/*.md         blank markdown
into   →    specs/001-user-auth/          spec.md · plan.md · tasks.md  ← real artifacts
gated by →  .specify/memory/constitution.md
اسکریپت چه کسی صدا می‌زند کاری که می‌کند
common.sh همهٔ اسکریپت‌های دیگر کتابخانهٔ مشترک: ریشه را با بالا رفتن تا دیدن .specify/ پیدا می‌کند، فیچر جاری را از SPECIFY_FEATURE یا feature.json درمی‌آورد، مسیرها را چاپ می‌کند و قالب را با اولویت overrides → preset → extension → core حل می‌کند.
create-new-feature.sh /speckit-specify شرح فیچر را به نام kebab تبدیل می‌کند، شمارهٔ بعدی (۰۰۱، ۰۰۲، …) را می‌زند، specs/<NNN-name>/ می‌سازد، spec-template.md را به spec.md کپی و feature.json را می‌نویسد.
setup-plan.sh /speckit-plan فیچر جاری را پیدا می‌کند، اگر plan.md نبود از قالب می‌سازد و مسیر spec و plan و branch را به‌صورت JSON برمی‌گرداند.
setup-tasks.sh /speckit-tasks اگر spec.md یا plan.md نباشد شکست می‌خورد — نمی‌شود از فازها پرید. سندهای اختیاری موجود را فهرست می‌کند و قالب tasks را برمی‌گرداند.
check-prerequisites.sh analyze، implement و مراحل بعدی دروازه‌بان مشترک با پرچم‌های --require-spec، --require-tasks، --include-tasks، --paths-only و --template NAME. پیش‌فرض: پوشهٔ فیچر و plan.md باید موجود باشند.
resolve-template.sh skillها و extensionها پوستهٔ CLI روی resolve_template_content؛ قالب نام‌برده را چاپ می‌کند تا کسی منطق bash را کپی نکند.

شکافی که باید ببندیم

نصب روی feature_numbering: sequential تنظیم شده، ولی فیچرهای موجود تاریخ‌محور و داخل features/ هستند. اسکریپت‌ها دنبال specs/* با پیشوند NNN- می‌گردند، نه specs/features/YYYY-MM-DD-…. تا وقتی این را یکی نکنیم، skillهای /speckit-* و SDD قبلی از کنار هم رد می‌شوند.

قدم بعدی عملی

اول .specify/memory/constitution.md را پر کنید (یا /speckit-constitution را بزنید) با قوانین واقعی پروژه، تا /speckit-plan یک دروازهٔ واقعی داشته باشد نه placeholder. بعد دربارهٔ شماره‌گذاری تصمیم بگیرید یا با templates/overrides/ قالب‌ها را به ساختار فعلی نزدیک کنید.

Beyond the SDD fundamentals

Spec Kit operationalizes specifications—it is more than an idea

We have already explored the philosophy of Spec-Driven Development: specifications become the source of truth, and code becomes their expression. This session focuses on GitHub Spec Kit, the open-source toolkit that puts that philosophy into practice with a CLI, templates, and agent commands.

Define before you build. Specifications are executable, not disposable documents.

Tooling

What is Spec Kit?

A ready-to-use toolkit for any AI coding agent

Spec Kit provides a ready-made spec-driven process—or lets you bring your own. It is extensible, community-driven, and designed for an entire organization.

SDD in general

The power inversion: specifications govern code. Any AI assistant can support it when the team maintains the discipline.

Spec Kit

A practical implementation: CLI, templates, core commands, extensions, presets, and bundles.

Technology independence

SDD is a process, not something tied to a particular language, framework, or technology stack.

Constitution

Architectural DNA in memory/constitution.md

The constitution is the file that holds your project's fixed rules. The agent reads it before every plan, and the plan must pass its Constitutional Compliance section. Every example below applies to the same onboarding feature shown on slide 16.

Feature logic starts in a standalone package so it can be tested and reused without any UI. Do: packages/onboarding → nextStep(), validateStep()
Don't: apps/web/app/onboarding/page.tsx → nextStep()

That same package must run from a terminal so its behavior is inspectable without a browser: text in, text out, JSON for structured data. onboarding-cli validate --json < profile.json

An approved test comes first and must fail before any implementation exists. 1. onboarding.test.ts → expect(nextStep('PROFILE')).toBe('PREFERENCES') → FAIL
2. nextStep() → PASS

A component more than one app needs moves to a shared package; a component only one app needs stays inside that app. Do: packages/ui/src/Stepper.tsx → apps/web + apps/admin
Don't: apps/web/components/Stepper.tsx + apps/admin/components/Stepper.tsx

Data fetching happens in a Server Component, and 'use client' reaches only the interactive leaf. Do: app/onboarding/page.tsx → await getOnboardingState()
Do: OnboardingForm.tsx → 'use client'
Don't: app/onboarding/page.tsx → 'use client'

Question 3 — Where is the Constitution stored?

Articles I–III come from Spec Kit's own template; your team writes Article IV onward. When a plan violates one of these rules it stops at Phase -1 (the Simplicity, Anti-Abstraction, and Integration-First gates), and the agent must justify it under Complexity Tracking.

The install folder

What exactly is installed inside .specify/?

.specify/ is Spec Kit's install folder, not your product specs. Select any node to see what that file really does. This tree comes from the actual install in this repository: version 1.0.4, the cursor-agent integration, bash scripts.

Select a file

This folder holds four very different kinds of thing:

  • Install configuration at the root: what was installed, for which agent
  • Project law in memory/
  • Blank templates in templates/
  • Executable scripts in scripts/bash/

The two manifests are only install receipts.

One detail that matters for this team: because invoke_separator in integration.json is -, our commands are written /speckit-specify while the official documentation shows /speckit.specify. They do the same thing.

Scripts

The deterministic half: scripts/bash/

The Cursor skill writes prose; the scripts create paths. Agents call them with --json so they read real paths and templates instead of inventing folder names. 

     you / Cursor skill  /speckit-specify, /speckit-plan, …
runs →  .specify/scripts/bash/*.sh        create dirs, check files, resolve paths
copies →  .specify/templates/*.md         blank markdown
into   →    specs/001-user-auth/          spec.md · plan.md · tasks.md  ← real artifacts
gated by →  .specify/memory/constitution.md
ScriptCallerWhat it does
common.sh Every other script The shared library: finds the project root by walking up to .specify/, resolves the current feature from SPECIFY_FEATURE or feature.json, prints path variables, and resolves templates through overrides → presets → extensions → core.
create-new-feature.sh /speckit-specify Turns the description into a kebab short name, takes the next sequential prefix (001, 002, …), creates specs/<NNN-name>/, copies spec-template.md to spec.md, and writes feature.json.
setup-plan.sh /speckit-plan Resolves the current feature, creates plan.md from the template when missing, and returns the spec, plan, and branch paths as JSON.
setup-tasks.sh /speckit-tasks Fails when spec.md or plan.md is missing—you cannot skip phases. Lists whichever optional design docs exist and returns the composed tasks template.
check-prerequisites.sh Analyze, Implement, and later steps The shared gate checker, with --require-spec, --require-tasks, --include-tasks, --paths-only, and --template NAME. Default validation: the feature directory and plan.md must exist.
resolve-template.sh Skills and extensions A CLI wrapper around resolve_template_content that prints a named template, so nobody has to copy the bash resolution logic.

Our repository today

.specify/ next to our existing specs/

This repository already had its own SDD practice. Spec Kit is a second, more generic pipeline—specify → plan → tasks → implement with a constitution gate—and the two layouts do not line up yet.

OwnerThe Spec Kit CLIOur own product SDD

Feature layoutspecs/001-short-name/ → spec.md · plan.md · tasks.mdspecs/features/2026-09-06-…/ → spec.md · plan.md · validation.md

The gap to close

Init chose feature_numbering: sequential, while the existing features use a date plus a nested features/ directory. The scripts look for specs/* with an NNN- prefix, not specs/features/YYYY-MM-DD-…. Until we align them, the new /speckit-* skills and the older SDD skill talk past each other.

The practical next step

Fill .specify/memory/constitution.md—or run /speckit-constitution—with our real project rules so /speckit-plan has an actual gate instead of placeholders. Then decide on numbering, or use templates/overrides/ to bend the templates toward the structure we already have.

Ad-hoc prompting

  1. One large prompt to the agent
  2. Code without a durable specification
  3. Decisions disappear into chat history
  4. Manual rewrites when requirements change

Spec Kit

  2. Plan records technical choices
  3. Tasks, contracts, and test scenarios live on a branch
  4. Implement and Converge drive alignment
